**Assessment:** This is a useful React/TypeScript procurement-triage application with an unusually careful reviewed-import workflow. It is not clean or succinct overall. The UI is too concentrated in one file, important tests are disconnected from normal development commands, and staff-only access is not enforced at the current database boundary. Address access and correctness before doing a broad refactor.

Reviewed the current working tree, including uncommitted changes, application code, configuration, migrations, both repository Edge Functions, workflow libraries, tests and skill/workflow routing. Inspected CSS structure/tokens/responsive/focus rules, not every declaration or visual layout. Compared with the supplied [review](C:/Users/sherr/.codex/attachments/c66fd0d4-42e6-4c19-a20b-efc6ac8dc894/Pasted%20text.txt). Used read-only live Supabase policy/function inspection; did not invoke paid generation, change database permissions, deploy, edit application code or certify the entire Git history for secrets.

**What the code does**

- React/Vite renders an authenticated lead-management workspace. `procurement.ts` loads canonical leads and sources, maps payload/dedicated fields into display records, and supplies RPCs for notes and stage changes.
- Staff-facing queues organize the sales workflow: new, interested, applied, hold, won, lost, not-interested and withdrew. Notes/history, selection, filters and bulk stage changes are supported. Open means a sales-workflow queue; it does not establish an open procurement solicitation.
- Realtime lead notifications and focus events schedule refreshes. Request sequence counters protect against stale fetch responses. Selected-lead history is fetched separately.
- The SAM Edge Function performs private server-authorized API searches, validates parameters, records query/response audits and keeps the SAM key server-side. CLI scripts register sources/geographic requests, stage evidence, prepare reviewed SQL packages, test them offline, apply them, and verify live readback. These are operator/agent workflows, not an automatically scheduled research service.
- Companies/email outreach and Generate remain disabled product areas with substantial prototype code. The older generation handler writes `spin_*` tables rather than the canonical procurement intake/lead pipeline; re-enabling it requires integration work as well as security work.

**Findings, ordered by importance**

1. **P1 — Anonymous users can read the staff application's lead and source tables.** Fresh live inspection confirmed SELECT grants to `anon`, enabled RLS, and PERMISSIVE policies `procurement_leads_read` / `procurement_sources_read` with `USING (true)`. Separate staff policies check `procurement_members`, but permissive policies combine as alternatives: the unrestricted policy defeats the intended staff restriction. This is an actual configuration problem, not merely a missing migration. Review policy names/grants and remove the broad path for tables intended to be staff-only; test anonymous, authenticated non-member and approved-member access. Public source metadata may be a deliberate separate choice, but private sales fields must not inherit that choice. [Read-only evidence](C:/Users/sherr/janitorial-lead-gen/outputs/procurement-access/code-review-20260930-access.json).

2. **P1 — Stage updates require login but not staff membership.** Both live stage RPCs are SECURITY DEFINER, callable by `authenticated`, and check only that `auth.uid()` is non-null. A non-member account can use the RPC independently of the React screen. The UI offers account signup, although current Auth signup eligibility was not inspected. A membership table already exists: use it consistently instead of creating a second authorization model. Disabling signup alone does not protect against an existing non-member account. [RPC definition](C:/Users/sherr/janitorial-lead-gen/supabase/migrations/20260911000600_procurement_other_reason_detail.sql:19), [signup](C:/Users/sherr/janitorial-lead-gen/src/app/AppShell.tsx:1448).

3. **P2 — Selecting a lead removes imported research qualifications from the UI.** The mapper adds `status_note`/`verification_notes` to notes, but `refreshContractHistory` replaces the entire notes array with user-note table rows. Selection and each contracts refresh call that function. For a record with research notes but no user notes, the array becomes empty. Board-approval/execution qualifications can consequently disappear while the award remains displayed. Preserve research context separately from editable user notes and merge it when rendering. The database evidence remains intact. [Overwrite](C:/Users/sherr/janitorial-lead-gen/src/app/AppShell.tsx:737), [initial mapping](C:/Users/sherr/janitorial-lead-gen/src/lib/procurement.ts:174). This was missed by the supplied review and by the pure mapping tests.

4. **P2 — Date-only values shift to the previous calendar day in US time zones.** `new Date('2026-09-17')` produces a UTC instant, then labels/filters use local dates. Running the actual date-label helper with `America/New_York` returned `Due Sep 16, 2026`. The same pattern occurs in key-date formatting and date-range filtering. Handle calendar dates separately from timestamps; preserve timezone semantics for true deadlines. [Label](C:/Users/sherr/janitorial-lead-gen/src/app/AppShell.tsx:3155), [key dates](C:/Users/sherr/janitorial-lead-gen/src/app/AppShell.tsx:3172), [filter](C:/Users/sherr/janitorial-lead-gen/src/features/contracts/contract-utils.ts:30).

5. **P2 — Missing source URLs become clickable invalid links.** Running the current helper with an empty string returned `https://`; this passes the card's truthy check. Return no link for empty/invalid input and validate allowed protocols. [Helper](C:/Users/sherr/janitorial-lead-gen/src/app/AppShell.tsx:3189), [consumer](C:/Users/sherr/janitorial-lead-gen/src/app/AppShell.tsx:1822).

6. **P2 — Reused leads are not associated with a newly reviewed request.** The planner sets `request_reason` only for new leads; the SQL creates request links only when that reason is present. An existing lead reviewed for another valid request therefore gets no new geographic relationship, even when the reviewer supplies a factual match reason. A dry-run using actual stored identities reproduced `existing_link: false` and `proposed_reason: null`. Create a reviewed missing request link independently of whether the lead itself is new; preserve existing links and conservative match status. [Planner](C:/Users/sherr/janitorial-lead-gen/scripts/lib/reviewed-batch.mjs:182).

7. **P2 — Fresh manual captures have an incomplete amendment path.** Intake equality includes retrieval time, request IDs and authorization text. A new retrieval time alone makes the same source/external record fail with `Changed intake evidence`. Keeping originals immutable is good, but the prescribed new amendment identity cannot use the generic manual-target path to attach to the old record: the target guard requires the same external ID except for legacy page captures, which new manual staging rejects. Provide a reviewed document/record amendment relationship so refreshes can preserve originals without creating duplicate contracts. [Capture equality](C:/Users/sherr/janitorial-lead-gen/scripts/lib/research-persistence.mjs:70), [target guard](C:/Users/sherr/janitorial-lead-gen/scripts/lib/reviewed-batch.mjs:128).

8. **P2 — The manual metadata guard does not cover the complete stored payload.** `safeMetadata` checks `f.payload`, then the code adds evidence, field bases and authorization without checking the assembled object. A dry-run with an `api_key` placeholder in `field_basis` was accepted into the manifest. This does not establish that real credentials have leaked; it demonstrates a gap in the stated protection. Validate the complete stored structure, use a bounded schema for evidence metadata and keep private access state separate. [Assembly](C:/Users/sherr/janitorial-lead-gen/scripts/lib/research-persistence.mjs:66).

9. **P2 — The UI does not paginate and can show an incomplete queue.** The loader requests every lead and its entire payload, with no range/cursor or total count. Once an API row limit is reached, queue counts and available results can silently represent only part of the table. Realtime changes trigger full reloads, increasing cost and latency as data grows. Use pagination/server-side filters and lighter list fields, with explicit total/loading state. Current configured row-limit value was not inspected. The CLI snapshot collector already paginates, so this concern is specifically the UI loader. [Loader](C:/Users/sherr/janitorial-lead-gen/src/lib/procurement.ts:111).

10. **P2 — A successful stage write can be reported as a failed save when history loading fails.** Both action handlers await history before applying returned stage rows to UI state; history failure enters the same save-error path even after the RPC committed. Realtime may later reconcile, but the immediate state/message is misleading. Apply confirmed mutation results first, then handle history refresh as a separate recoverable read. The dedicated bulk control already uses one atomic bulk RPC; its subsequent history reads still grow per lead. [Single action](C:/Users/sherr/janitorial-lead-gen/src/app/AppShell.tsx:950), [bulk action](C:/Users/sherr/janitorial-lead-gen/src/app/AppShell.tsx:978).

**Good**

- Stage SQL validates input, locks rows, records history transactionally, pins search paths and revokes anonymous RPC access. Bulk updates lock in deterministic ID order and avoid duplicate-input processing. These are useful foundations; authorization needs tightening.
- Import packages bind reviewed payloads, schema and SQL hashes; reject drift; test rollback/readback/replay; preserve user data; and block blind retries after an uncertain outcome. This is considerably better than ad hoc upserts.
- SAM search restricts endpoint/filter choices, caps pagination, refuses redirects, uses a timeout, audits before network activity and redacts its API key. `verify_jwt=false` is not automatically an exposure here because the handler requires a server secret in the `apikey` header.
- Mapping, query errors and stale-response handling are separated from much of the UI. Historical/provisional distinctions are preserved in the data layer. CSS has reusable brand/neutral tokens, focus indicators and responsive breakpoints.
- The frontend uses a publishable Supabase key; server authorization is obtained through the CLI or Edge Function environment rather than embedded in React.

**Bad: readability and maintenance**

`AppShell.tsx` is approximately 3,194 lines, has about 52 state-hook calls, and contains a line 1,078 characters long. It combines authentication, two workspaces, fetching, history, filters, dialogs and prototype outreach. Components/types exist elsewhere but AppShell duplicates types, stage mapping and filter defaults. Utility and workflow files also compress many branches/statements onto single lines: fewer lines are not the same as succinct, understandable code. Extract cohesive hooks/components and format code before imposing elaborate new abstractions. There is no need to rewrite the whole application.

The standard `npm test` runs only four Vitest tests. The 31 Node workflow tests need a separate command. Several depend on ignored operational snapshots/packages, and PGlite is loaded from an external installation using `PROCUREMENT_RESEARCH_DIR`. They pass here but are not a reproducible clean-checkout/CI suite. Declare/configure the engine and commit minimal sanitized fixtures; retain private production snapshots separately. Add composed UI tests for selection/history and calendar dates. ESLint's rules target TS/TSX; substantive `.mjs` scripts are not covered by those rules.

**Ugly: security drift and competing data paths**

The database's membership policy and unrestricted read policy coexist; the repo lacks baseline core-table DDL/RLS migrations to reproduce and review that state. The legacy Generate implementation uses a second set of tables and broad `spin_*` read policies. Its local handler has no caller authorization and permissive outbound URL fetching; it must be gated and integrated before activation. However, live function listing did **not** include `spin_generate_contracts`, so a current live exploit through that named endpoint was not established. Other deployed functions without repository source were outside this review.

Repository hygiene also needs work: `.netlify` and `supabase/.temp` files remain tracked, and a 34,995,268-byte deployment ZIP remains in HEAD/history even though it is deleted in the working tree. Capture files also increase repository weight. Only `.env.example` is currently tracked among `.env` files; neither the supplied review's archive-content claim nor a complete historical absence-of-secrets claim was independently established here. Avoid distributing deployment archives containing dependencies or local configuration, and decide deliberately what audit artifacts belong in Git.
