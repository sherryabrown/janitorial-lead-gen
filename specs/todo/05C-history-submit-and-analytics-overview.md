# 05C — Submitted History searches and compact analytics

Status: planned. Initiating prompt and shared requirements: [amendment](05-schedule-results-and-history-amendment.md), incorporated in full. Depends on accepted 05A and 05B. This is the final amendment before integrated Phase 6.

## Implementation

1. Give global `RunHistory` an explicit submitted-search mode; keep schedule-scoped run lists automatically loaded. Reuse current history endpoint, filters, offset pagination, abort/generation protections and owner cleanup. Initial entry has from/through = today's date in America/Chicago, no rows, and concise Submit instruction. Do not mount/load selected run logs/evidence before selection. Fetching schedule filter choices is allowed; result queries are not.
2. Separate draft and applied filters. Submit validates date order/bounds, snapshots all draft filters, resets result pagination and loads matching runs. Enter submits; buttons prevent duplicate concurrent submissions. Changes to draft do not fetch, relabel old results or trigger resource owner Refresh. Hide prior results or mark them explicitly as previous submitted scope while filters are dirty; Submit remains the obvious next action. Empty/no-match differs from not submitted.
3. Replace initial/global History Refresh with Submit. After failure, one Retry repeats the failed applied request, including a failed page, without applying edited drafts. New Submit applies new drafts. Do not render both a parent Refresh and local Submit/Retry for the same results. Extend existing `ReadAction`/read-owner behavior narrowly; other workspace refresh semantics stay unchanged. Active run detail polling and explicit run refresh remain as before.
4. Back from a selected run restores the successfully submitted filter set, loaded page and focus; returning within that navigation chain may reload the same applied query, never a broad default. Fresh History entry starts empty/today. Store draft/applied state separately, owner-scoped, version storage format and clear on sign-out; old stored blank-date filters must not auto-submit. Deep links with a validated run ID still open that explicit run; they do not imply a background global search. Handle midnight/CT DST with existing timezone helpers.
5. Global Stats: use the attachment's metric hierarchy already shared through 05B; keep period, schedule, type, More filters and one read owner. Remove the Runs table and its sort/order/pagination UI, without removing backend history/reporting contracts used elsewhere. No speculative charts. Retain concise processing/attention, usage and timing sections with unknown/partial/coverage explanations and existing definitions. The default remains last seven days; Stats may continue current automatic filter application and one Refresh/Retry. Do not change that to submitted searches merely because History changed.
6. Remove frontend run-page-only state/props/imports when unused; request only needed report content using existing bounded endpoint options or a small backward-compatible summary-only option. Ensure aggregation covers all matching runs, not just an initial page, and server snapshot/cohort links remain consistent. Do not remove public API fields/callers without usage checks. Keep run count as reporting context, not another Runs list.
7. Use 05A drilldowns for all saved-lead totals/categories and matching issue-detail destinations for collection/validation counts; this distinction is confirmed, not pending product approval. Label issues explicitly rather than “candidates/leads needing attention.” All valid leads automatically import into `procurement_leads` for manual and scheduled runs using existing validation and duplicate checks, with no added approval gate. Preserve as-imported category semantics, distinct outcome precedence, state grouping, zero/unknown/partial, cost/credits and reservations. Review all Settings count surfaces for exact destinations and ensure issue counts do not inflate lead totals or combine overlapping metrics silently.
