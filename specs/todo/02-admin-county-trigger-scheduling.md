## Persistence and controls

Add procurement_schedules (id, name, config, version, enabled, timezone, frequency/local_times/weekdays/month_day, next_due_at, owner/actor IDs, created/updated); procurement_schedule_occurrences (schedule_id, config_version, due_at, frozen config/actor, trigger_id, state, missed/overlap reason, timestamps), unique schedule_id/due_at. Validate county scope and categories/date window policy through the same preview. Version/CAS on edits, audit pause/resume/edit actions. Recalculate next due without altering in-flight run snapshots. Removing a county affects future occurrences only; explain this in UI. Deleting/archiving a schedule retains occurrence history, and does not cancel an active run unless the user explicitly chooses Stop run.

Authenticated list/create/update/pause/resume/run-now endpoints; scheduler dispatch is a separately authenticated private route without browser JWTs. Use fixed reviewed destination/auth, no arbitrary URLs. Scheduled actor comes from persisted owner authorization; disable new occurrences on revoked/deleted account authorization. Do not save expiring user access tokens for future runs. Schedule Run now creates a manual occurrence using current saved configuration and does not shift next due.

State-source scheduling uses the same CRUD/occurrence/lease machinery with a source target instead of county IDs. Finding a state source creates/reuses its saved independent trigger but does not silently enable a recurrence. Source schedules remain paused/unconfigured until explicitly saved/enabled. County schedule edits never enqueue or reschedule associated state-source updates. Link state results to associated county review scopes without recapturing. One independent source occurrence can serve many counties; do not fan it into county collection jobs.

## Recurrence and reliable wake

Confirmed cadence: daily with one or multiple selected local times, weekly, and monthly in America/Chicago. Store sorted unique daily local_times (HH:mm), weekly selected weekday(s) plus local time, and monthly day-of-month plus local time. Reject empty/duplicate/invalid times and unsupported combinations. Use explicit chosen daily times, not an inferred interval. Offer compact Add time/Remove time controls. Monthly days 29–31 run on the last valid day in shorter months; show that rule alongside the control. Every selected daily time generates its own due occurrence. Persist IANA timezone and compute due instants server-side; no browser timers. Handle daylight saving explicitly: nonexistent local time runs once at the first valid time afterward; repeated local time runs once at the first occurrence. Freeze the computed due UTC instant with the occurrence. Display local time, zone and next due; test both DST transitions.

Use one Supabase pg_cron dispatcher with pg_net/private Vault authorization to wake the existing backend (direct fixed backend endpoint or a minimal server-auth Edge bridge). Verify extension/grant/project availability during build; do not invent live support or silently choose paid infrastructure. Keep business recurrence in schedule rows, not one Cron job per county. Tick only when due schedules or pending continuations exist; no artificial keepalive. Persist and observe HTTP send/outcome; network response loss cannot create duplicate occurrence.

Under atomic lock/lease claim: revalidate schedule enabled/version/owner, claim due occurrence, snapshot configuration and relative date windows, advance next due, enqueue shared trigger work, commit. Dispatching runs executes bounded existing stages; persisted pending continuations are woken on later ticks even with no browser. Keep heavy work serialized on current host. An active overlapping occurrence is logged Skipped: previous run active; do not accumulate unlimited backlog. For outage recovery, coalesce missed due times into one catch-up occurrence and log the missed range; never replay months of inference unnoticed. Unknown external outcomes stay reconciliation-required before automatic retry. Pausing prevents future occurrences/automatic sends, but preserves current audit/evidence.

Rolling category windows resolve relative to each occurrence's local date; changes-since baseline uses last successful comparable source/category observation, with original fingerprints/evidence preserved. Do not replace existing change semantics without explicitly documenting/testing the chosen baseline. Fixed bounded historical windows can remain an advanced manual choice; schedules must not accidentally reuse expired static windows.
