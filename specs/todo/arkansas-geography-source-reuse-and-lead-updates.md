## Implementation phases

### 1. Geography and source routing

1. Inspect existing geography references. Adapt `procurement_geographies` and `procurement_place_counties` to import reviewed Arkansas GIS incorporated municipalities and spatial county links, retaining source/version evidence and stable GIS IDs. Preserve legacy Census rows and references without selecting them for new requests. Do not use ZIP or `spin_geography` for procurement routing. Add only the missing request/route fields and constraints; reuse existing target, capability and task tables. Model a county request's municipality selection on the individual search request, not as a saved county default. Handle a municipality with multiple county relationships by asking for the relevant county when needed.
2. Add a server-side scope resolver and route planner. Normalize names to IDs; reject ambiguous/unmapped names. Emit city routes first, then county, then Arkansas state routes, deduplicating shared sources. Record why each source applies and keep agency coverage distinct from work-performance match.
3. Provide a documented backend command that the agent can invoke from a chat request. For a county request, return the incorporated municipality list and wait for the user's selection in chat before creating the request. Show known and unknown routes separately so known county/state checks can proceed even while municipality-source discovery remains open.
4. Extend `scripts/lib/research-persistence.mjs` and the snapshot/schema tooling to read/write verified capability and request associations with optimistic guards. Backfill existing public source metadata only after review; do not infer a working method from a URL or old ledger status.
5. Tests: municipality→county→state ordering; municipality list and per-request confirmation; county-only selection; cross-county municipalities; clean display names and GIS classification; aliases/ambiguity; shared source deduplication; mixed known/unknown routes; stale or missing capability; migration constraints and read policy.

### 2. Deterministic checks of known sources

1. Define a versioned source adapter contract for public document, browser-supported retrieval, and API methods: supported categories, jurisdiction/filter mapping, query windows, pagination terminal condition, normalized identity, parser version, evidence output and bounded failure behavior. 2. Drive `procurement_coverage_tasks`, `procurement_jobs`, and `procurement_runs` from route plans. Use stable dedupe keys, leases/checkpoints and complete-page accounting. 3. Send verified captures to the existing stage → explicit review → test → apply → readback path in `scripts/procurement-workflow.mjs` and `scripts/lib/reviewed-batch.mjs`. Leave unresolved records pending. Keep forecast, opportunity and award coverage and classifications separate.
4. Run each known city/county/state route even when another route requires discovery; do not delay known county/state checks because the city source is unknown.
5. Tests: known source bypasses discovery; zero versus blocked/partial; pagination gaps, rate limits and resume; duplicate/revised records; SAM modification identity; location uncertainty; package hash, rollback, replay, protected user fields and verified readback. Extend `tests/sam-capture.test.mjs`, `tests/research-persistence.test.mjs`, `tests/reviewed-workflow.test.mjs`, and SQL/integration tests as appropriate.

## Implementation decisions for build

- Checks are user-triggered while the backend is validated. No recurring schedule is authorized by this plan.
- Use the existing Supabase function-secret pattern for supported server API credentials. Ask the user to enter newly issued secrets through the approved Supabase secret-management route when agent access cannot do so securely; the action alert must give precise steps without including the secret. Investigate each interactive portal's actual sign-in method before choosing session or secret storage; do not treat a Supabase API secret as a reusable browser session. Public tables and the ignored ledger must not contain credentials.
- The Arkansas GIS Office's incorporated municipal boundary and county boundary layers supply selectable municipality names, classifications and municipality-county links. Review a complete snapshot, especially multi-county intersections, before import. Census place rows remain only for legacy references; `spin_geography` and ZIPs are not used for procurement routing. Add a broader named-community list only if later evidence shows it finds useful leads.
- Geography requests are initiated by the user in chat during these phases. The build adds a backend command and chat-facing result contract, with no application navigation or request-screen changes.

## Success criteria

For a confirmed Arkansas scope, the system shows the resolved ordered routes and uses verified stored methods without research. Missing methods enter evidenced discovery/access work and, once verified, run through the same deterministic path. Every source/category ends with a truthful coverage state and next action. New or changed evidence reaches reviewed intake/import with replay-safe readback; unclear records remain pending. User-facing lead stages, notes and existing queues continue to behave as they do now.
