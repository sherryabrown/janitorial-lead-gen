## Implementation decisions for build

- Checks are user-triggered while the backend is validated. No recurring schedule is authorized by this plan.
- Use the existing Supabase function-secret pattern for supported server API credentials. Ask the user to enter newly issued secrets through the approved Supabase secret-management route when agent access cannot do so securely; the action alert must give precise steps without including the secret. Investigate each interactive portal's actual sign-in method before choosing session or secret storage; do not treat a Supabase API secret as a reusable browser session. Public tables and the ignored ledger must not contain credentials.
- The Arkansas GIS Office's incorporated municipal boundary and county boundary layers supply selectable municipality names, classifications and municipality-county links. Review a complete snapshot, especially multi-county intersections, before import. Census place rows remain only for legacy references; `spin_geography` and ZIPs are not used for procurement routing. Add a broader named-community list only if later evidence shows it finds useful leads.
- Geography requests are initiated by the user in chat during these phases. The build adds a backend command and chat-facing result contract, with no application navigation or request-screen changes.

## Building in phases

Build one numbered phase at a time. Phase 2 now has offline-tested SAM, verified public-method and registered entry-point runners. It remains open until the migrations/functions and bounded live checks are verified, registered sources without geography are mapped from evidence, and sources requiring a category-specific method are verified or explicitly blocked. An entry-point check alone does not complete category coverage. Do not move to Phase 3 on the strength of an entry-page response. For each phase, implement its code and tests, report the verified behavior and remaining dependencies, and leave this plan in `specs/todo/` until all three phases pass. Move it to `specs/done/` only after phase 3 and end-to-end validation. A phase-scoped request should explicitly override the build-code skill's usual move-to-done step for a successful partial build.

## Success criteria

For a confirmed Arkansas scope, the system shows the resolved ordered routes and uses verified stored check methods without repeating source research, including official non-API URLs and check timing. Registered sources needing a method are identified separately from genuinely unknown sources. Every source/category has a durable run or an explicit blocker, truthful coverage state and next action. New or changed extractable evidence reaches reviewed intake/import with replay-safe readback; checked content needing interpretation remains pending with its provenance. User-facing lead stages, notes and existing queues continue to behave as they do now.
