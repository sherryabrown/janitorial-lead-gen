Plan an addition/edit/revamp to Phase 3 Schedule Details: put the latest run in the run list instead of separately; make saved county selections view-only with accessible guidance to archive and recreate to change them; restrict Quick actions to View, Edit, Disable, with Disable offering Pause, Archive, Delete; include SAM and state sources in the same creation/edit/disable experience with suitable non-map selection; retain Overview, History, Logs, Related geography, Sources tabs; research comparable admin layouts and recommend a basic wireframe with clear focus, list/detail association and distinct sections. Preserve unrelated behavior and Netlify production.

## Outcome and design recommendation

Use a focused detail page within the existing Admin workspace, replacing the table while viewing one schedule. Keep its identity, scope and lifecycle above the five tabs. A single Back to schedules link restores the same filters, loaded page, scroll and originating row focus. Do not append details beneath a long table or squeeze the existing ten-column table beside a narrow drawer. The list keeps its existing columns; this amendment reduces action clutter rather than removing metrics.

This is a recommendation informed by primary design-system guidance, not a requirement to install those libraries:

- [PatternFly primary-detail](https://www.patternfly.org/patterns/primary-detail/design-guidelines/): maintain an obvious relationship between selection and details, including matching identity and preserved list context. Its side-by-side pattern is useful when both regions fit; this product's wide metrics table and five rich tabs favor a focused detail surface.
- [Carbon data table](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines): keep resource lists scannable and put row-specific actions in a consistent menu, with search/add controls in the toolbar.
- [PatternFly tabs](https://www.patternfly.org/components/tabs/design-guidelines/): group related content under clear tabs, with visible active state and responsive overflow.

Research checked 2026-10-20. Reuse current brand/CSS tokens, neutral surfaces, #FF914D selection/primary-action accents, existing typography and controls. No design-system dependency. [Static wireframe](../../docs/mockups/admin-schedule-detail-revision.html) contains list, detail, editor, disable and mobile sketches. All sample values are illustrative, not live analytics.

Rendered planning previews: [desktop](../../docs/mockups/admin-schedule-detail-desktop.png) and [mobile](../../docs/mockups/admin-schedule-detail-mobile.png). Both checked without document overflow at 1440/390px; implementation still requires the complete automated, keyboard and 320px acceptance below. No application tests were run for this documentation-only amendment.

### Screen hierarchy

1. List: Schedules heading, Add schedule, compact filters, table. Schedule-name link and Details open identical details. Keep a visible row Run now button beside the floating menu. Menu contains exactly Details, Edit, Disable; Disable opens Pause/Archive/Delete as a submenu. Remove direct Stats/History/Sources shortcuts. Keep their functionality in details, one tab away. Preserve workspace manual Run now.
2. Detail: Back to schedules, schedule name, target/scope, textual lifecycle; Run now is the single principal execution action, with secondary Edit and Disable. Frequency, timezone and next run occupy a compact facts strip. No separate latest-run summary, metrics card, View last run or last-run evidence shortcut. Existing list last-run columns remain.
3. Tabs: Overview, History, Logs, Related geography, Sources. Use visible active underline and semantic tab/tabpanel behavior with arrow/Home/End navigation and focus indication. Existing URL section enum can remain `overview`/`history`/`logs`/`geography`/`sources`; label Overview without claiming full Stats is built.
4. Overview: distinct Schedule settings section (read-only configured work/window/AI policy as actually stored), then Runs section. Newest real run is the first ordinary row under the existing newest-first ordering; no duplicate pinned row. Run table shows timestamp, outcome, new/updated/unchanged, duration basis, AI usage and View/Logs/Sources actions using existing reporting and completeness. Period/all-time analytics remains phase 4; do not fabricate totals here.
5. History: clearly separated Scheduled occurrences (including skipped/blocked without a run) and Schedule changes (actor/time/version where available). Label occurrence versus actual run outcome. Actual runs in Overview include manual Run now as well as scheduled runs exactly once. No fabricated run for a skipped occurrence.
6. Logs: run selector/list plus a clearly titled selected-run step log, with run identity/date/origin visible. Sources: labeled saved run evidence and selected-run context. Related geography: county/city or state associations in a distinct table/list, labeled saved configuration versus current/derived relationship. Reuse existing run detail/evidence routes; do not build a new collector or global source catalog in this amendment.
7. On navigating to a run, show the schedule-to-run relationship in the heading/back path. Return restores schedule tab and run-list filter/page. Refresh/back/forward/deep links retain this context. A schedule outside current list filters is explicitly identified in detail; never silently change filters to make it appear.

Whitespace, section headings and thin dividers separate content. Use one modest neutral settings surface, not a card for every metric or a column of undifferentiated definition lists. IDs/version are secondary disclosure. Short labels plus contextual help replace instructional paragraphs. Loading/error/empty states belong to their section.

## Scope and lifecycle rules

### County membership

- Create: choose county/county set using existing map/checklist/chips, display cities and an inline resolved scope summary, then Save schedule with background validation. County selection is then immutable for that schedule ID. Manual-run map remains editable.
- Details/edit/disable/delete context: show saved county names as text (not misleading disabled selection widgets). Info control text: “To change counties, archive this schedule and create a new one.” Available by hover, focus and tap; do not put required guidance only in hover.
- Preserve ability to change name, cadence, enabled state and currently editable non-geography collection/window settings. Do not lock all config by comparing whole scope_hash: that also includes category/city snapshots. Compare normalized saved county membership (deduplicate/sort IDs), not input order or display name. Target-kind switches must not circumvent the county lock. Creation still validates current registry scope and preview hash.
- SQL save mutation must check immutable county identity under the same row lock/version transaction, not only hide the map or compare before the RPC. Service rejection gives actionable archive/recreate guidance. Direct RPC/service-role misuse cannot change a saved county schedule into another target to bypass it. No new browser RPC privilege.
- Do not silently adopt changed registry city snapshots, repair a blocked scope, or alter current `scope_changed` scheduling behavior in this UI change. Existing preview/confirmation protections stay; if a saved schedule needs recreation, show that action clearly with known blocker. Historic run snapshots remain untouched.
- A different target/source selected during new-schedule creation is supported; a saved county target cannot be converted. For existing SAM/state schedules retain existing supported editable non-county options; don't introduce a new target-conversion feature. Show saved target as identity in edit.

### Unified schedule editor

One Add schedule opens a focused editor with target choices: Counties / State source / SAM.gov. Choice is explicit and keyboard/touch usable. Counties show map; State source shows searchable saved independent-state-source options with agency/source name and existing associated geography, never an Arkansas-map gesture; SAM shows fixed Arkansas statewide scope and the existing category/lookback controls. Keep each target's current execution and duplicate-schedule rules.

Common name/cadence/enabled/save controls use existing ScheduleFields/service. Reuse existing target-specific validation/rolling windows, saved-source identities, preview hashes, idempotent create keys and version conflicts. State-source list empty/error has an honest scoped explanation and existing next step; no fake statewide choice, automated county discovery on open, or silently created source. Switching unsaved targets must retain target-specific drafts or explicitly offer discard; editing must never overwrite manual county/SAM drafts. Open/create/edit/disable/back/reload does not execute work.

### Save schedule without a separate review step

The existing TriggerForm and SamSection use explicit preview then confirmation; AdminScreen/SAM submit require a preview hash and confirmed_scope. This was a validation/scope check, not a requirement for a separate screen. Replace it only for schedule creation/editing across county/state/SAM with one Save schedule button (Save changes when editing) and Cancel. Keep scope/cities, target, cadence/timezone, windows and next run visible inline. Update that summary through the existing preview endpoint on valid form changes, with debounce/abort/generation checks, without creating schedules or runs. No Review schedule, Review SAM schedule, Confirm and save or extra acknowledgement click.

On Save, capture the current draft and version, obtain/revalidate its canonical preview through the existing service, compare it with the currently displayed resolved scope, then submit the same draft with the current preview_hash/confirmed_scope and existing idempotency/version handling. Reuse service/endpoint contracts; do not remove backend validation or blindly mark a materially different hidden scope confirmed. If membership/city coverage or target identity changes unexpectedly, show the corrected inline summary and specific error, stop the write and let the user save the corrected form; this is an exceptional changed-data case, not a routine review page. Recurrence/window preview refresh and changes to the draft cannot save an older version. Disable duplicate submissions, retain drafts on failure and preserve acknowledgement-loss keys. Save success opens the saved schedule details and refreshes its row. Invalid input focuses its field/message; preview failure cannot silently save.

Manual-run confirmation and all existing collection/import guards outside schedule saving remain unchanged. No schedule save should enqueue work outside the existing scheduler semantics. Test this one-click save path for all three targets and both create/edit, including races, stale preview, version conflict, failure and retry; no schedule mutation occurs during typing or background preview.

### Quick actions and Disable

Visible row action: Run now, using the existing saved-schedule handler, not the current manual draft. Row floating menu: Details, Edit, Disable only; no row expansion or hover-only activation. Details opens the same focused schedule surface as the schedule name. Detail retains secondary Edit/Disable and primary Run now. Archived rows allow Details; Run now/Edit/Disable stay unavailable with a concise reason.

Disable opens a nested floating submenu with Pause, Archive, Delete directly under that row's menu, or anchored to the detail Disable button. Remove the intermediate Disable dialog, action-choice screen and Continue button. Pause/Archive execute the selected action directly with pending/success/error feedback; do not require a generic second confirmation. Delete alone retains a compact named destructive confirmation; it does not reopen the removed Disable chooser. Existing Pause/Archive effects and never-run deletion guard remain unchanged.

Add a focusable/tappable information control beside the Quick actions column heading. Concise help: “Run now starts this saved schedule. Details opens its settings and runs. Edit changes schedule settings. Disable: Pause stops future runs; Archive keeps history; Delete is available only before any run. Current runs continue.” Keep eligibility-specific explanations at unavailable menu items as well; do not rely on the column tooltip for required feedback. Re-enable paused schedules through Edit.

Reuse the existing portaled ActionMenu. It currently supports only flat actions; add optional submenu support without changing retained callers. Parent and submenu form one focus/outside-click boundary. Click/tap/Enter/Space or ArrowRight opens Disable; ArrowLeft closes only the submenu and returns focus to Disable; Escape closes one level, then the parent, returning focus appropriately. ArrowUp/Down and Home/End navigate the active menu. Closing a parent closes children. Hover may supplement activation but must never be required. Reposition/flip/clamp both menus to the viewport; on narrow screens the submenu can occupy the same floating panel with a Back control. No row height changes, clipping, document overflow or accidental mutation from opening/closing menus.

| Choice | Effect |
| --- | --- |
| Pause | Stops future scheduled runs; keeps configuration/history. Existing in-flight/manual runs are not cancelled. Resume remains available through Edit → enabled state, using existing validation/blocker checks. Already paused shows Pause unavailable/already paused. |
| Archive | Stops future scheduling, retains runs/evidence/audit history; existing archive semantics remain; execute from submenu with concise feedback. |
| Delete | Only eligible when no actual run has ever been created or associated. Confirm named schedule; history-bearing schedules show disabled Delete with “This schedule has run. Archive it to keep its history.” |

Delete is new backend functionality, not a renamed Archive or UI-only hide. No existing DELETE route exists. Implement an authenticated version-checked control endpoint consistent with `/v1/schedules/:id/<action>` conventions, with safe eligibility/reason returned by existing list/detail projection if needed (do not issue per-row probes). Eligibility must inspect trigger links AND occurrence run links/history, not only last_run display fields. Queued/running/uncertain work is ineligible. Never delete Leads, imports, evidence, usage, triggers or run snapshots.

Use the existing schedule-management advisory lock and row-lock order for atomic eligibility, disable and delete versus scheduler enqueue/Run now/save. A new SQL RPC is appropriate; service validation alone is insufficient. Repeat acknowledgement/retry must produce a stable safe outcome without acting on a different schedule/version. Preserve authentication, actor and RPC grants/RLS restrictions. Do not add table DELETE permission to browsers.

Never-run schedules can still have creation/edit events and skipped/blocked occurrences. Retain their audit data: proposed minimal strategy is an additive deletion tombstone on the schedule record, disabled/no-next-due and excluded from schedule pickers/default/all-status listings; retain safe historical identity for schedule events/global history. This is a logical deletion of an eligible schedule, not permission to hide run-bearing schedules. Name reuse and idempotency retry must not accidentally resurrect it. Eligibility/visibility must be checked in save, controls, enqueue/tick and detail reads. Verify latest schema/view/RPC definitions before choosing migration details; if using a different strategy, prove no audit/FK loss and document it. No bulk destructive cleanup/backfill.

Pending requests, version conflict, network acknowledgement loss and already-archived/deleted states use existing safe mutation/reload conventions. Do not automatically retry a different destructive decision. If another run wins the deletion race, return “Schedule has run; archive instead” and preserve it. Menu/submenu closing or destructive-confirmation cancel does not mutate. Focus returns to triggering control; after delete return to list with concise success and correct refreshed count/page.

## Decisions and boundaries

Confirmed: selectable counties at creation, immutable afterward; Delete only for never-run schedules, archive those with runs.
