Status: implemented and accepted locally, 2026-10-22; release pending. Requirements and initiating prompt: [amendment](../todo/05-schedule-results-and-history-amendment.md), incorporated in full. Depends on completed Phase 5; no dependency on 05B/05C. No layout overhaul in this phase.

## Objective and implementation

1. Audit actual deployed event schema/RPC definitions and existing verified import metadata before adding anything. Reuse `procurement_schedule_events.summary`; do not create another audit table. Identify all writers, including save, pause/resume/archive/delete and system owner changes. Keep occurrence-only events distinguishable from actual schedule changes.
2. Add a versioned, allowlisted field-difference payload for future successful schedule mutations, inside the existing transactional SQL mutation. Capture name, recurrence/timezone, lead categories, window policy, work flags, state membership where editable, enabled/archive lifecycle. Preserve immutable county rules and existing scope/version/idempotency checks. Compare old/new canonical data, not client claims. Store no secrets or full provider configs. No-op or replay must not fabricate repeated changes; failed/concurrent writes create no successful event. Creation may show initial allowed values; deletion follows current never-run rules.
3. Extend the existing events DTO with sanitized differences and accurate actor/time/version; keep historical sparse events as `Details not recorded`. No historical backfill from current settings. Add stable tie-break ordering and bounded existing pagination. Keep skipped/run events available in execution context.
4. Extract/reuse the verified identity selection currently inside `admin-analytics.mjs` so aggregate values and link cohorts use the identical outcome precedence, categories, date bounds, origin, schedule and grouping logic. Reuse verified receipt records; never infer “new” or “updated” from current mutable lead rows. Add an authenticated read endpoint for paged metric member IDs (or an equivalently bounded existing endpoint extension), with validated run/schedule/report scope, metric and snapshot/as_of. Avoid returning unbounded IDs in the summary, giant URLs, per-row requests or a new persistent report database. Include a metric descriptor with the same coverage/known-subtotal metadata.
5. Implement an optional typed Leads drilldown in `src/app/AppShell.tsx` and Admin callbacks. Scope is additive to existing Leads query/rendering: visible `Results from …` filter, exact verified IDs, clear-scope action and return-to-origin. Do not let default Open/New queue hide members without clearly labeling an additional filter; use a scoped all-stage result presentation while retaining every lead's stage and all stage controls. Clearing restores prior queue/filter context. Do not globally change queue defaults. Do not silently intersect away closed leads or report stale zero.
6. Resolve IDs server-side in bounded pages; handle missing/deleted/inaccessible lead records honestly with unavailable count rather than substituting others. Verify authorization for both report scope and canonical Leads; IDs/URL values are not authorization. Keep read APIs read-only. Refuse expired/changed snapshot matches with a clear reload path rather than silently broadening the cohort. Preserve current records with historical as-imported classification.
7. Wire existing saved-lead count surfaces using a shared metric-link component: schedule last-run new/updated counts, schedule totals, run rows/details and analytics. Keep hooks usable by subsequent phases; do not break existing generic View leads actions. Partial links say `N known`; unknown without IDs is not a link. Zero has a meaningful empty destination. All valid leads automatically import into `procurement_leads` through existing validated, duplicate-safe manual/scheduled services; add no approval gate. Collection/validation issue counts link to their exact issue details and next actions, not to general Leads or unrelated records. Use issue labels instead of “candidates/leads needing attention”; retain existing metric definitions and separate issue types rather than silently summing overlapping counts. A related saved Lead may have its own explicit link.
